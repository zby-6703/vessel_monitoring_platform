# 2026-10-31 真实过船变焦失败与高清流修复

## 本次故障证据

用户报告的过船在 15:07:30 已触发生产录像。选船时参考船高约 7.5%，建议倍率约 9.36×，受竖直取景范围限制实际选择已标定 **2×**，不是界面固定倍率设置中的 3×。

- 15:07:30：开始录像并请求 2×。
- 15:07:35：发生可重试的网络传输异常，重试 2×。
- 15:07:40：进入尝试缩回 1×。
- 15:07:45：没有得到镜头到位确认，本轮结束，进入错误状态。

生产片段 `eb871951b9304ffd9f03b4d49fa6a90d` 已保存 **13.96 秒**、1280×720，状态为中断，原因为 `zoom_failed`。指令记录中 2×、2×、1× 均没有 settled 确认。因此不能声称实物完全没动，也不能把该片段标为成功放大录像。

旧逻辑在网络异常后停止整个循环，使采集仍有画面但后续目标无法进入详细识别和录像；界面错误还把网络传输问题与倍率标定问题混在一起。另一个边界是：首次网络异常后正在重试，录像侧期限先到，原来的网络原因尚未保存，仍可能被当作终止类到位失败。

## 用户授权的辅码流调整

用户明确确认没有其他系统使用辅码流2，并同意调整测试。通过设备实际 Profile 与编码器绑定核实其为独占配置 `002`，主码流编码器为另一配置。

| 参数 | 调整前 | 调整后 |
| --- | --- | --- |
| 编码 / 分辨率 | H264 / 1280×720 | H264 / 1280×720 |
| 帧率上限 | 25 | 12 |
| 码率上限 | 2048 kbps | 1024 kbps |
| 编码间隔 | 1 | 1 |

只修改该辅码流的速率控制字段，保留其分辨率、画质、GOP、音频及其他原生字段；不改设备主码流。设备写入后重新读取，结果逐项一致。本机平台改用 `MediaProfile002` 实际声明的取流 URI，`LIVE_CAPTURE_FPS_OVERRIDE=12`，避免按旧 25 fps 生成重复帧。录像侧镜头到位容忍改为 45 秒，仍不将超时当作位置确认。

原始编码配置、目标配置、设备选项及环境备份保存在被 Git 忽略的 `data/camera-stream-tuning/2026-10-31/`：`aux2-before-and-target.json`、`aux2-verified.json`、`env-before-aux2.bak`。环境备份含私有配置，不提交或公开。

可逆实现为 `camera_stream_setup.MediaStreamConfigurator`：明确指定辅码流 Profile，拒绝主码流和共享编码器，核对设备声明范围，只允许三个速率字段变化，拒绝覆盖并发改动，提供 restore 恢复原生配置。遵循 [ONVIF Media Service 5.5.5](https://www.onvif.org/specs/srv/media/ONVIF-Media-Service-Spec-v1706.pdf)；配置变更后重新取得 URI 并重新建立视频连接。

## 程序修正

1. ONVIF 连接池及 Digest 状态复用，保留新鲜 WSSE nonce、原请求超时和认证限制；传输失败丢弃旧连接，配置变化及服务关闭释放连接。依据 [HTTPX Clients](https://www.python-httpx.org/advanced/clients/)。
2. 保留首次传输错误的分类，避免重试途中超时被误判为永久设备故障；普通重试成功后清除此标记，非网络错误不被误当作可恢复。
3. 传输失败后保留本轮原视频，有限尝试恢复 1×。只有实际反馈确认 1× 才恢复锁定目标判断，本轮不再重复放大。保底视频带 `zoom_fallback` 标记并按中断归档，下一轮可以重新选船；持续失败仍受最长录像时长约束。
4. 恢复预算耗尽后仍可通过后续只读 1× 反馈恢复，未知倍率或迟到回复不能冒充到位。手动停止取消主动恢复。
5. 界面显示恢复中及保底录像；实际有活动录像时保持 REC。历史录像区分计划倍率与已确认倍率，不再无条件标注“含放大与回 1× 过程”。
